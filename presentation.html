Problem Statement

The Pain Behind School Payments Today

📋 Manual Processing Everywhere

Finance teams rely on spreadsheets, email threads, and manual data entry to track thousands of parent payments. Every handoff introduces delay and human error.

🔀 No Single Source of Truth

Payment data lives in disconnected systems — POS terminals, bank statements, accounting software — making reconciliation a multi-day ordeal every month.

⏳ Approval Bottlenecks

Transfers awaiting sign-off sit in inboxes without visibility. Reviewers don't know what's pending; approvers have no audit trail of who reviewed what.

🏦 Bank Integration Gaps

Bank transfers are initiated manually and outcomes tracked via phone calls or periodic log-ins. Failed transfers are discovered days late, causing cash-flow issues.

💸 Fee Calculation Errors

Platform fees, processing charges, and net school amounts are calculated in ad-hoc spreadsheets. Disputes arise monthly over who owes what to whom.

🚫 Zero Accountability Trail

When errors occur, there is no log of who changed what and when. Audit season becomes a forensics exercise rather than a straightforward report pull.

Assumed context: this system targets a payment aggregator or ministry of education that collects parent fees and distributes net amounts to individual schools after deducting platform fees.

Senior authority — final financial sign-off

Always-on background engine

  • Receives and ingests incoming payments
  • Calculates fees and updates ledger entries

  • Executes retry logic on failures
  • Runs daily reconciliation and settlement jobs
  • Triggers notifications at each status change

🤖 System acts on: schedule triggers, approval events, bank callbacks

Segregation of Duties: No single user can both review and approve the same transaction. The system enforces this at the workflow layer, creating a four-eyes principle for all financial movements.

Transaction Lifecycle

Status Flow — Every State Explained

Awaiting Review → Under Review → Approved → Transferred → Completed

Awaiting Review

Payment captured. No human action taken yet. Sits in the review queue. Timer starts (SLA clock).

Under Review

A reviewer has claimed and is actively examining the transaction. Locked to prevent duplicate processing.

Approved

Senior approver has signed off. System queues bank transfer. Fee calculation is finalized and locked.

Transferred

Bank API call has been successfully sent. Awaiting bank-side confirmation. Net amount is in-flight.

Completed ✓

Bank confirmed successful credit to school IBAN. Ledger marked final. Settlement record created.

Failed ✗

Bank returned error or retries exhausted. Amount NOT debited. Transaction flagged for manual resolution.

Failed Partial Settlement — also valid terminal/intermediate states

State transitions are enforced by the system — no user can manually jump a transaction to Completed. Every transition generates an immutable audit log entry.

System Architecture

Platform Modules — Conceptual View

🧾 Transactions Module

The core intake layer. Captures all incoming payments, assigns unique IDs, enforces the status machine, and drives the approval workflow. The source of truth for what money came in.

🏦 Bank Integration Layer

Abstraction over bank APIs (SWIFT, local RTGS, IBAN-based transfers). Handles authentication, transfer initiation, status polling, and webhook callbacks. Isolates the rest of the system from bank-specific quirks.

📒 Ledger (Accounting Engine)

Maintains double-entry bookkeeping records for every financial event. Gross amount in, fee deducted, net out. Immutable ledger lines — nothing is ever deleted, only corrected by contra entries.

⚙️ Settlement Engine

Runs daily (and on-demand) to aggregate approved transactions into settlement batches, compute net positions per school, and trigger bulk or individual bank transfers. Handles partial settlements.

🔔 Notifications Service

Event-driven alerts via email, SMS, and in-app. Fires on every meaningful status change — approval needed, transfer completed, retry exhausted. Configurable per user role and urgency level.

📊 Reporting & Analytics

Pre-built dashboards for daily volumes, fee summaries, school-level net positions, SLA compliance, and failure rates. Export to CSV/Excel for finance teams. Supports custom date range filtering.

Design Principle: Each module is independently deployable and communicates via internal events. This means the Bank Integration layer can be swapped for a different bank partner without touching the Transaction or Ledger modules.

💰 Ledger Entry Breakdown

DR: Receivables Account +1,000

Money received from parent. System holds the gross amount.

CR: Platform Revenue +25

Platform fee recognized as income at approval time.

CR: Bank Fees Payable +5

Transfer cost accrued against the gross amount.

CR: School Payable +970

Net owed to school. Released to bank on transfer confirmation.

🔑 Key Financial Rules

  • Separation of concerns: A transaction record (what happened) is distinct from a bank transfer record (how the net was sent). One transaction → one or more transfer attempts.
  • Fee lock: Fees are calculated and locked at approval time, not at transfer time. Rate changes don't retroactively affect in-progress transactions.
  • No money moves without approval: The bank transfer API call is gated — it cannot trigger unless transaction status = Approved.
  • Failed transfers do not debit: If bank API returns failure, no ledger debit is posted. School Payable remains intact until retry succeeds.
  • Settlement batching: Multiple small transactions to the same school in one day can be batched into a single bank transfer to reduce fees.

Error Handling & Retry Logic

When Things Go Wrong — The Safety Net

Error Type Root Cause System Response Retry Policy Escalation
Bank API Timeout Bank takes too long to respond Mark transfer as Pending · Do not debit ledger 3 retries: 5m → 15m → 60m Alert Finance team after attempt 3
Invalid IBAN School IBAN failed bank validation Mark transfer Failed · Flag school account No auto-retry — IBAN must be corrected Alert school admin + approver immediately
Insufficient Funds Platform operating account low balance Queue transfer · Pause settlement batch Retry after manual top-up confirmation Immediate CFO-level alert
Duplicate Transaction Same payment received twice Block second entry · Flag for review No transfer until manually resolved Reviewer notified to confirm or reject duplicate
Bank System Down Bank maintenance / outage Queue all transfers · Halt new initiations Auto-resume polling every 30 mins Status banner shown in dashboard to all users
Partial Settlement Some items in batch fail, others succeed Split batch · Mark failed items separately Individual retry for failed items only Settlement report flags partial completion

Retry Rules Summary

  • Max automatic retries: 3 attempts
  • Backoff strategy: Exponential (5m · 15m · 60m)
  • After 3 failures: Manual intervention required
  • No retry for: Invalid IBAN, Rejected by Bank (final)
  • All retry attempts logged in Audit Trail

Financial Safety Guarantees

  • No ledger debit posted until bank confirms success
  • Idempotency keys prevent duplicate bank API calls
  • Every retry uses a new transfer record — no mutation
  • Failed transactions never auto-complete
  • All failures visible in real time on dashboard

Reconciliation & Accuracy

How We Ensure Every Riyal Balances

🔄 Daily Reconciliation Job

23:00 — Settlement Cut-Off

System stops accepting new transactions into today's batch. All approved transactions are locked for settlement.

23:05 — Aggregate Per School

Settlement engine sums all approved, same-day transactions per school. Calculates total gross, fees, and net.

23:10 — Initiate Batch Transfers

Single bank transfer per school for the day's net amount. One bank call per school, reducing transfer costs.

Next Day 06:00 — Bank Response Check

System polls bank for overnight transfer confirmations. Updates all transaction statuses to Completed or Failed.

06:30 — Reconciliation Report

System compares internal records against bank statement. Flags any discrepancies automatically for Finance review.

✅ Accuracy Mechanisms

Ledger Balancing Check

After every batch, system verifies: Total DR = Total CR across all ledger entries. Any imbalance triggers immediate alert. No batch closes with an unbalanced ledger.

Bank Statement Matching

Each confirmed bank transfer is matched to an internal transfer record via bank reference number. Unmatched items (in bank but not in system, or vice versa) are flagged as Exceptions.

Three-Way Reconciliation

System checks: (1) Transaction record, (2) Ledger entry, (3) Bank transfer record all agree on amounts. If any two of three disagree, a discrepancy ticket is auto-raised.

Assumption: Bank provides either a webhook callback on transfer completion or a pull-based statement file (MT940/CAMT.053) that the system imports and auto-matches daily.

Security & Access Control

Built Secure From the Ground Up

🔑

Role-Based Access Control (RBAC)

Every feature, screen, and API endpoint is gated by role. A Reviewer cannot reach the Approve button — it does not render for them. Permissions are defined centrally and version-controlled.

🔐

Multi-Factor Authentication

All users require MFA at login. Approvers performing transfers above a configurable threshold (e.g. SAR 50,000) are challenged with a second factor at the point of approval, not just at login.

🛡

Data Encryption

IBAN and banking credentials are encrypted at rest (AES-256) and in transit (TLS 1.3). Encryption keys are managed via a dedicated Key Management Service — never stored alongside data.

📍

IP Allowlisting & Session Controls

Admin and Approver accounts can be restricted to organization IP ranges. Sessions expire after configurable inactivity. Concurrent sessions from multiple devices trigger security alerts.

🔍

API Security (Bank Layer)

Bank API credentials are stored in a secrets vault — never in code or environment variables. Each outbound bank call is signed with a request HMAC. Responses are verified before processing.

🚨

Anomaly Detection

Automated alerts fire on: unusual approval volume from one user, IBAN changes shortly before a transfer, login from new geography, or approval outside business hours above threshold.

🔒 Segregation Enforced By System

The same user cannot review AND approve the same transaction. This is a hard constraint in the workflow engine, not just a policy document.

🔏 IBAN Change Approval Gate

Any change to a school's IBAN requires a secondary approver confirmation and a 24-hour cooling period before it can be used for transfers.

📋 Penetration Testing Cadence

Assumed: quarterly external pen tests + annual security audit by an accredited third party as part of financial regulatory compliance requirements.

Bank Integration Architecture

How We Connect to the Banking System

🏦 Integration Methods Supported

REST API (Primary)

Modern banks expose REST endpoints for initiating transfers, checking status, and receiving webhooks on completion. EduPay's Bank Adapter handles auth, signing, and retries transparently.

SFTP File-Based (Legacy Banks)

For banks that don't offer real-time APIs, EduPay generates ISO 20022 / MT103 payment files, drops them on a secure SFTP, and imports the bank's response files to update statuses.

Bank Webhooks (Event Push)

Where available, the bank pushes transfer confirmations or failure notices to EduPay's secure webhook endpoint. This enables near-real-time status updates without polling overhead.

🔌 Bank Adapter Pattern

Bank Integration · Adapter Layer
Settlement Engine
   ↓ calls
BankAdapter Interface
   → initiateTransfer(amount, iban, ref)
   → getTransferStatus(bankRef)
   → onWebhookReceived(payload)

Implementations:
   SAMABankAdapter → REST API
   LegacyBankAdapter → SFTP files
   SandboxAdapter → for testing

The adapter pattern means adding a new bank requires only implementing the adapter interface — zero changes to the Settlement Engine, Transaction, or Ledger modules.

🔄

Idempotency Keys

Every bank API call includes a unique idempotency key derived from the transfer ID. If a network timeout causes a duplicate call, the bank deduplicates it — money is never sent twice.

🗂

Bank Reference Tracking

The bank's own reference number (e.g. SWIFT end-to-end ID) is stored on every transfer record, enabling exact reconciliation against bank statements.

🧪

Sandbox & Production Modes

Each bank adapter ships with a sandbox mode that simulates success, failure, and timeout responses — enabling full end-to-end testing without touching real bank accounts.

School Onboarding & Account Management

Getting Schools Ready to Receive

Before a school can receive any settlement, its account must be fully verified and approved. This is the onboarding gate that protects against fraud and ensures financial accuracy from day one.

🏫 School Onboarding Steps

Step 1 — Basic Registration

School name, commercial registration number, contact email, phone. Admin account created for the school's finance contact.

Step 2 — Document Upload

Commercial license, VAT certificate, authorized signatory ID. Documents reviewed by Operations team within 2 business days.

Step 3 — IBAN Submission & Verification

School submits their bank IBAN. System performs IBAN format validation immediately. A micro-deposit test (e.g. SAR 1.00) is sent to confirm the account is live and matches the school name.

Step 4 — Fee Tier Assignment

Operations assigns the applicable platform fee rate (e.g. 2.0%, 2.5%, 3.0%) based on the school's contract tier. This rate is locked and version-tracked.

Step 5 — Account Activated

School status set to Active. School admin receives welcome email with portal access. They are now eligible to receive settlements.

⚙️ Ongoing Account Management

IBAN Change Request

School submits a change request with supporting documents. Requires dual approval from Finance + Operations. 24-hour holding period before new IBAN goes live. Old IBAN logged in history permanently.

Fee Rate Amendment

Any fee rate change requires Operations approval and takes effect from a specified future date — never retroactively. Historical rates are preserved for audit and settlement accuracy.

Account Suspension

If a school has outstanding disputes or compliance issues, their account can be suspended: incoming payments still accepted but settlements are held until the account is reinstated.

School Portal Access

Each school's finance contact gets a read-only view: their own settlements, transaction history, and downloadable statements. They cannot see data for other schools.

Technology Stack

Built on Proven, Scalable Technology

Technology choices are driven by three principles: reliability (money cannot be lost), auditability (every action traceable), and maintainability (the team can own it long-term).

Frontend

React / Next.js
Server-side rendering for fast initial load, SEO-ready admin screens
Tailwind CSS
Consistent design system, responsive layouts
React Query / Zustand
Server state management, optimistic UI updates

Backend & API

Node.js / NestJS
Structured, modular API with built-in DI and validation
PostgreSQL
ACID-compliant, row-level locking for ledger integrity
Redis
Job queues, session storage, idempotency key cache

Infrastructure

AWS / Azure (Cloud)
Multi-AZ deployment, 99.9% uptime SLA
BullMQ (Job Scheduler)
Reliable cron jobs for settlement, retries, reconciliation
Docker + Kubernetes
Container orchestration, horizontal scaling, zero-downtime deploys

🔒 Financial Data Constraints

  • All money amounts stored as integers (fils/halala) — no floating point arithmetic
  • All database transactions use serializable isolation for ledger writes
  • Audit log table has a database-level trigger — no application code can bypass it
  • Point-in-time recovery enabled on database (RPO < 5 minutes)

📦 Third-Party Services

  • SendGrid / AWS SES — transactional email delivery
  • Twilio / Unifonic — SMS for critical alerts (Arabic + English)
  • AWS KMS — encryption key management
  • DataDog / New Relic — application performance monitoring

Risk & Compliance Framework

Risks Identified — Controls in Place

Risk Category Likelihood Impact Control / Mitigation
Fraudulent IBAN change Fraud Medium High Dual approval + 24h hold + micro-deposit verification + audit log
Double payment to school Operational Low High Idempotency keys on all bank API calls + transfer state machine prevents re-submission
Bank API credential leak Security Low Critical Secrets vault (KMS) + no credentials in code or config files + quarterly rotation
Reviewer/Approver collusion Fraud Low High Enforced segregation of duties + anomaly detection for unusual approval patterns
Settlement job failure Operational Medium Medium Job monitoring with instant alert + automatic retry + manual re-trigger UI
Regulatory audit request Compliance High Medium Complete audit trail + on-demand compliance report export + immutable logs
Database corruption / data loss Technical Very Low Critical PITR backups (RPO <5min), daily snapshots, multi-AZ replication, tested restore process
Fee rate misconfiguration Operational Medium Medium Fee locked at approval time, not transfer time + version-controlled rate history per school

📋 Compliance Standards

  • SAMA Open Banking framework
  • PCI-DSS (if card data in scope)
  • ISO 27001 information security
  • Local data residency requirements

🔍 Ongoing Risk Reviews

  • Monthly security access review
  • Quarterly penetration testing
  • Annual external audit
  • Continuous anomaly monitoring

🛑 Business Continuity

  • Failover region for all services
  • RTO target: < 1 hour
  • Manual override for bank transfers
  • Disaster recovery tested bi-annually
